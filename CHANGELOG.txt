Phase 9: release
  WHAT: The v1.0 deliverable. publish.bat rewritten, the published exe exercised
        from an empty folder, the last untested format closed, the version made
        single-source, README finished, and TypographyFontFileViewer-v1.0.zip
        built.
  WHY:  Phase 9 asks for a release that has been run rather than assumed, and a
        reported exe size and cold-start time.

  THE EXE, MEASURED:
        - 63,298,809 bytes (60.4 MB), one file, nothing beside it.
        - Window up in 838, 882, 889, 992 and 1,016 ms across five runs from a
          folder containing only the exe, with a font on the command line. The
          slowest was the very first launch, which also unpacks the native
          libraries. Target: under 2 s. MET.
        - Launched again with dotnet off PATH and DOTNET_ROOT pointed at a folder
          that does not exist: window in 979 ms. That is as close as a machine
          with .NET installed can come to proving the exe is self-contained; a
          genuinely clean PC is still someone's job.

  WHAT THE EMPTY-FOLDER RUN FOUND:
        - 42 files in the font folder, including a zero-byte .ttf and 5 KB of
          random bytes named .woff2, listed as 44 entries (two collections
          expand) with exactly 2 marked unreadable. The broken WOFF2 shows
          "Expected the tag 'wOF2' but found '$I??'." in the gallery rather than
          failing the row.
        - Ctrl+D wrote Favorite Fonts\Inter-Regular.ttf beside the exe; after a
          restart the star was still on the right row and the status bar read
          "44 fonts - 1 star - 2 unreadable".
        - Renaming, deleting and overwriting the displayed font from another
          process all succeeded while the app had it open, and the app carried
          on. Nothing is file-locked.
        - Beside the exe afterwards: the exe, TypographyFontFileViewer.json and
          Favorite Fonts\. No log file, because nothing went wrong.

  .DFONT IS NO LONGER UNTESTED:
        It was the one v1.0 format with no automated source, because no Windows
        tool writes a Mac data-fork suitcase and the corpus could not build one.
        tools/make-test-fonts.py now writes one from the documented resource-fork
        layout: an 'sfnt' resource per font, a type list, a reference list with
        24-bit data offsets, and the map that ties them together. FreeType reads
        the structure directly, which is what the app was relying on untested.
        The corpus gains TestSuitcase.dfont (two faces) and two tests: both faces
        enumerate separately with the DFONT badge, and the face renders two
        different strings differently, which a .notdef row would not.
        Verified in the published exe as well as in the tests.

  THE VERSION NOW HAS ONE SOURCE:
        The standing convention bumps the version in the csproj, the title bar
        and the zip name. Three hand-kept copies of one number drift, and a title
        bar claiming the wrong version is the sort of thing nobody notices until
        a bug report quotes it. New Core/AppInfo.cs reads the assembly version;
        the title bar, the About box and the crash dialog ask it, and only the
        csproj's <Version> is authoritative. Four new tests in ReleaseTests.cs
        guard the rest of the convention: the displayed version matches the
        csproj, the changelog has an entry for it, every PackageReference is
        listed in the README with its licence, and every extension the sniffer
        accepts appears in the README's format table.

  ONE README CLAIM WAS WRONG:
        The Known limits section first said colour fonts render as outlines.
        Checking it instead of trusting it: Segoe UI Emoji draws in full colour
        at every waterfall size, because the rasterizer already asks for
        FT_LOAD_COLOR and copies BGRA bitmaps through. The line became a feature
        rather than a limit. This is the second time in this project that a
        plausible sentence about the code was false; it is cheaper to run the
        thing than to reason about it.

  HOW:  - publish.bat now empties publish\ before building, so a file an earlier
          configuration produced cannot sit beside the exe and look like part of
          the deliverable. It fails loudly if the build fails or the exe is
          missing, and prints the size and the full contents of publish\.
        - README rewritten for a released app: a Running it section with the
          SmartScreen warning named, honest sizes and timings, a Known limits
          section, and Phase 9 marked done.
        - Deliverable: TypographyFontFileViewer-v1.0.zip, 57,650,280 bytes,
          holding the exe, README.md, CHANGELOG.txt, LICENSE.txt and the
          blueprint under one TypographyFontFileViewer-v1.0 folder. It is a
          build output, so .gitignore keeps it out of the repository rather than
          adding 57 MB of binary to every clone for ever.

  VERIFIED:
        302 tests pass, zero warnings. Every acceptance item in blueprint

Phase 8: hardening
  WHAT: The blueprint's Section 13.3 stress list, run and fixed. New
        tests/StressTests.cs and Services/FontEngineLimits.cs; the engine now
        reports its queue depth, the background metadata pass releases what it
        reads, and clipped text is no longer rendered beyond the clip.
  WHY:  Phase 8 asks for no crash, hang or file lock in any stress case, and
        Section 13.4 sets the performance targets. Both needed measuring rather
        than assuming.

  THE STRESS LIST, AS RUN:
        - 2,000 fonts including 50 zero-byte or corrupt files renamed to .ttf
          and .woff2: lists in well under the budget, marks exactly 50 as
          unreadable, leaves the other 1,950 alone, and keeps serving requests.
        - A 30 MB CJK font in every view and every panel: fine.
        - Deleting, renaming and overwriting the displayed font: no lock, no
          crash, F5 recovers. Overwriting shows the new font rather than the
          remembered one, which is what keying the face cache on length and
          last-write time is for.
        - Un-favouriting while viewing the favourites folder: covered since
          Phase 5.
        - Unicode names (Chinese, Arabic, Cyrillic, an emoji outside the BMP)
          and a path over 260 characters: listed and rendered.
        - A folder vanishing mid-use, standing in for a USB drive being pulled:
          empties cleanly and the next folder opens normally.
        - A held-down navigation key: the queue peaked well inside its bound and
          drained to nothing when released.
        - Every format in the corpus through every panel.

  TWO REAL IMPROVEMENTS, BOTH FOUND BY MEASURING:
        - The background metadata pass was caching every font it opened. It
          visits each one exactly once, so that filled the cache with fonts
          nobody had asked to look at while evicting the ones they had, and held
          a folder's worth of font data live. It now reads, describes and
          releases. A 2,000-font folder went from 476 MB to 297 MB after the
          sweep.
        - Gallery rows and waterfall lines are clipped at the panel edge, but
          were rendered to their full width first — at a readable size, more
          than half the bitmap was produced, cached and never seen. Rendering
          now stops at the clip.

  PERFORMANCE AGAINST SECTION 13.4:
        - Cold start to window: 0.7 to 1.3 s, against under 2 s.          MET
        - 500 fonts, list visible: well under a second.                   MET
        - Preview re-render after a keystroke: median comfortably inside
          the guard, against about 50 ms.                                 MET
        - Next or previous font: median inside the guard, against 100 ms,
          and that measures opening a font never seen before.             MET
        - Memory, 2,000 fonts open in the gallery: 297 MB after listing
          and the full metadata sweep, but 440 to 500 MB after scrolling
          the whole gallery repeatedly, against under 400 MB.          NOT MET

  ON THE MEMORY TARGET, HONESTLY: every cache is bounded and was re-tuned
        together in Services/FontEngineLimits.cs — they had been set separately
        and added up to 416 MB before the runtime had taken anything, which is
        over the whole budget. They now total 160 MB. What remains is not
        retained memory but churn: each render allocates a BGRA buffer, anything
        over 85 KB lands on the large object heap, and that heap is not
        compacted by default, so heavy scrolling leaves the working set high.
        It oscillates rather than climbing, and the app stays responsive
        throughout, but it is over the target and should be reported as such.
        The named fix is to pool the render buffers: BitmapSource.Create copies
        what it is given, so the buffer is free immediately afterwards. That
        needs RenderedText to expose a length-bounded view rather than a raw
        array, since a pooled array is larger than it was asked for, and it is
        the kind of change that causes intermittent corruption if hurried. It
        is written down rather than rushed at the end of a phase.
        A GC conserve setting was tried first and measured no benefit, so it was
        removed rather than left in as an unexamined tuning knob.

  STILL NEEDS A PERSON: a network share, a USB drive physically pulled
        mid-scan, 200% display scaling, and a second monitor at a different DPI.
        The DPI arithmetic is tested and the app is Per-Monitor V2, but nothing
        here substitutes for looking at it on two real screens.

  VERIFIED: 294 tests, all passing, zero build warnings. The exe is one file,
        60.37 MB.

Phase 7: search, subfolders, settings, polish
  WHAT: A search box, a subfolder toggle, three sort orders, a recent-folders
        menu, settings that survive a restart, and a global exception handler
        that writes to TypographyFontFileViewer.log beside the exe. New
        Core/SortOrder.cs; AppSettings grew from one field to fourteen.
  WHY:  The last of the blueprint's Section 7 to 10 behaviour. A folder of two
        thousand fonts needs a way to find one, and an app that forgets where
        you were every time you close it is tiring to use.
  HOW:  Search filters file name, family and style as you type, and the sidebar
        and gallery share the result because both bind to the same filtered
        collection. Sorting re-orders the underlying list rather than using a
        view's sort descriptions, because family names arrive from the
        background pass long after the rows do and a view would not notice them
        changing — so a family sort is also re-applied once that pass finishes.
        Settings are written on close and on Windows shutting down, atomically,
        with enums stored as names so the file stays readable.

  TWO BUGS FOUND ON THE WAY, both real rather than test-only:
        - Filtering through a WPF CollectionView tied the view model to the
          thread that created it, so any background continuation touching the
          list threw. The app happened to work because continuations resume on
          the UI thread, but it was a thread-affinity bug waiting for a day when
          one did not. Filtering is now done explicitly and the view model has
          no dispatcher affinity at all.
        - Superseding a render disposed the token source the previous request
          was still holding, which could turn a cancelled render into an
          ObjectDisposedException. Two overlapping rescans found it. Superseded
          sources are now cancelled and left for the collector, which is all
          they need.
        - A third, found by looking at the screen rather than the tests:
          refreshing the filter resets the bound lists, and a list clearing its
          own selection writes null straight back into the view model. Searching
          therefore blanked the preview even when the selected font was still on
          screen. The intended selection is now captured before the reset.

  DETAIL WORTH KNOWING:
        - Ctrl+F focuses the search, Esc clears it and hands focus back.
        - Navigation walks the matches, not the whole folder, so Ctrl+Down steps
          through what a search left on screen.
        - The sidebar header says "9 of 40 fonts" while a search is on.
        - A window position saved on a monitor that is no longer plugged in
          falls back to the default rather than opening off-screen.
        - A setting out of range — a hand-edited or damaged file — is clamped
          rather than trusted.
        - Settings written by a later version keep the fields this one does not
          understand.
        - The log records unhandled errors with a timestamp, the OS and the
          runtime version, and the app offers to carry on rather than closing:
          one failed render should not cost the user the folder they had open.
          Faulted tasks nobody awaited are recorded and never shown, since fast
          scrolling produces them routinely.

  VERIFIED: 280 tests, all passing, zero build warnings.
        - Six keystrokes of search across 1,000 fonts in well under the budget,
          with the folder itself untouched.
        - From the published exe: opening the corpus and switching to Gallery,
          then closing, wrote the window bounds, last folder, last selected
          file, recent folders and the view; relaunching with no argument at all
          brought all of it back.
        - "noto serif" matches nine of forty by family name — the files are
          called NotoSerif-*.ttf, so only the family match can find them — and
          the first match is selected and previewed.
        - Subfolder toggling rescans wider and narrower; sorting by family
          groups a family into one run and keeps the selection; the recent list
          stops at ten and moves a reopened folder back to the top.

Phase 6: the Glyphs and Info panels
  WHAT: The single-font view's panel strip is full: Preview, Glyphs and Info.
        New Core/GlyphDetail.cs, Services/BitmapLruCache.cs,
        ViewModels/GlyphMapViewModel.cs, ViewModels/InfoViewModel.cs,
        Controls/GlyphCellImage.cs, Views/GlyphMapView and Views/InfoView, plus
        MetadataReader.ReadGlyphDetail and RenderService.ReadGlyphDetailAsync.
  WHY:  The last two things the blueprint asks a font viewer to answer: what
        characters does this font actually have, and what does it say about
        itself. Both describe one selected font, which is why they sit beside
        Preview rather than beside the gallery.
  HOW:  The glyph grid is built as rows of cells rather than one wrapping list,
        because WPF virtualizes a stack and does not virtualize a wrap panel.
        Microsoft YaHei's thirty thousand glyphs become a few thousand row
        objects, and only the rows on screen exist. Each cell fetches its own
        picture and cancels when recycled, the same arrangement the gallery
        uses. Resizing the panel or the cells re-slices the rows.
        The Info panel adds a row only where the font supplies something, so it
        shows what is there rather than a column of blanks.

  DETAIL WORTH KNOWING:
        - Glyph measurements are read unscaled, in the font's own design units,
          so they describe the glyph rather than the size it happens to be drawn
          at and do not change as the slider moves.
        - A click copies the character, a double-click opens the detail overlay.
          WPF counts the clicks against the user's own double-click setting, so
          there is no timing to track.
        - The jump box takes U+00E9, bare hex, or the character pasted in.
        - SHA-256 is computed on request rather than on selection: hashing a
          30 MB CJK font to fill in a line nobody asked for would be rude.
        - Links in the Info panel open only http and https. A font's name table
          can hold any string at all, and handing an arbitrary scheme to the
          shell would let a font decide what runs.
        - The gallery's bitmap cache became generic so the glyph map could share
          it. The two are tuned differently: the gallery holds 300 wide rows,
          the glyph map 4,000 small squares.
        - Ctrl+1, Ctrl+3 and Ctrl+4 now reach all three panels from either view.

  VERIFIED: 259 tests, all passing, zero build warnings.
        - Microsoft YaHei: 29,905 characters laid out, scrolled 500 wheel
          notches into CJK Extension A with the app still responding, working
          set 424 MB.
        - The Info panel on a variable font shows family, names, version, format,
          glyph and character counts, metrics, embedding permission and both
          variation axes with their ranges and defaults.
        - Tests cover grid chunking and re-chunking, the jump box in all its
          forms including a character the font lacks, cell caching and its
          limits, glyph details for an ordinary glyph and for a space, info rows
          for variable and web fonts, links flagged and non-links not, fields
          omitted when absent, and hashing only on request.

  A TEST THAT EARNED ITS KEEP: the Phase 5 test asserting Ctrl+3 and Ctrl+4 fall
        back to Preview failed the moment those panels existed, which is exactly
        what it was for. It has been replaced by one checking all three panels
        are reachable, and the fallback is now tested at the converter instead,
        where it still matters for any panel added later.

  KNOWN: with the whole Windows font folder open and a 30,000-glyph map
        scrolled through, the working set reaches 424 MB against the blueprint's
        400 MB target. Bounded, not leaking. Phase 8 runs the stress list
        properly and tunes the cache limits.

Phase 5: favourites
  WHAT: Starring a font copies it into a "Favorite Fonts" folder beside the exe;
        un-starring sends that copy to the Recycle Bin. New
        Core/FavoriteEntry.cs, Services/HashService.cs,
        Services/SettingsService.cs, Services/FileRecycler.cs and
        Services/FavoritesService.cs, plus the star in the font list, the
        single-font header and every gallery row, a right-click menu, Ctrl+D,
        a Favorites button and two File-menu items.
  WHY:  Requirements R4 and R5. A favourite that was only a bookmark would break
        the moment the original moved or was deleted; a favourite that is a real
        copy of the font is something you can open, install or send to someone.
  HOW:  Identity is the SHA-256 of the file's contents, never its name — two
        unrelated fonts are often both called Roboto.ttf, and the same font
        renamed is still the same font. Checking a folder hashes almost nothing:
        a file whose size matches no favourite is ruled out for free, and only a
        size that matches is ever read. The files in the folder are the truth and
        the index in the settings file is only the fast path, so startup
        reconciles the two — a font dropped in by hand is picked up, an entry
        whose file has gone is dropped.

  CARE TAKEN, since this is the only code in the app that removes a file:
        - Un-favouriting can only ever delete inside the favourites folder. The
          check is explicit rather than implied, and tested on its own with
          traversal paths, even though reconciling rebuilds the index from the
          folder listing and so should never produce a name that could escape.
        - The font the user favourited *from* is never touched; only the copy.
        - Deletion goes to the Recycle Bin, because that copy may be the only one
          left — favourited from a memory card, a cleared download, a folder
          since tidied.
        - The recycler sits behind an interface so the test suite does not fill
          the developer's Recycle Bin on every run. One test exercises the real
          one, so the path everyone else fakes is known to work.
        - Copies go to a temporary name and are then moved into place, so an
          interrupted copy never leaves a half-written font looking real.
        - Settings are written the same way: a crash midway leaves the previous
          file intact, and a file that will not parse is renamed to .bad rather
          than deleted, because it is the user's data.
        - A folder that cannot be written to says so plainly and names itself,
          rather than quietly saving somewhere the user will never find.

  DETAIL WORTH KNOWING:
        - A different font wanting a name already taken becomes "Name (2).ext".
        - A Type 1 font brings its .afm and .pfm metrics, renamed to match, or
          FreeType would not find them beside their new font.
        - Favouriting any face of a collection copies the whole file, so every
          face in it shows the star.
        - Opening the favourites folder itself stars every row by definition,
          which saves hashing a folder to learn what it already knows.
        - Un-starring while that folder is on screen removes the row as well and
          moves the selection on, since the file it stood for has just gone.
        - Settings keep fields they do not understand, so a file written by a
          later version is not stripped by an earlier one.

  VERIFIED: 229 tests, all passing, zero build warnings. End to end from the
        published exe: Ctrl+D created "Favorite Fonts\Inter-Bold.ttf" and
        TypographyFontFileViewer.json beside it; the star was still right after
        a restart; Ctrl+D again removed the copy and emptied the index. Tests
        cover hashing identity, name collisions, renamed duplicates, Type 1
        companions, collections, reconcile after a manual add and a manual
        delete, a recycler that refuses, an unwritable folder, and the
        delete-safety guard.

  NOT YET DONE: the favourites count in the sidebar header is live, but sort
        order, search and the subfolder toggle are Phase 7.

View switch: single font or gallery   (requested, outside the phase plan)
  WHAT: The tab strip is gone. A segmented switch in the header moves between
        two views — Single font and Gallery — and the gallery gained four named
        sizes: S (16 pt), M (28 pt), L (44 pt) and XL (72 pt), alongside the
        slider it already had. New ViewModels/ViewMode.cs and three converters;
        MainWindow now shows one of two views rather than hosting tabs.
  WHY:  Asked for directly. Both views already existed as tabs, but tabs say
        "panels of the same thing", and these are two answers to different
        questions: "what does this font look like?" against "which of these
        fonts do I want?". A switch says that, and the named sizes save aiming
        at a slider for the sizes anyone actually wants.
  HOW:  Radio buttons sharing a group, styled as one control, bound to a
        ViewMode enum through EnumToBooleanConverter; the views themselves swap
        on EnumToVisibilityConverter. The size presets are positions on the same
        scale the slider moves along rather than a separate setting, so picking
        Large and dragging the slider to 44 do the same thing and a preset
        lights up whenever the slider lands on it. Both views stay loaded, so
        switching keeps each one's scroll position; the hidden one unloads its
        rows, which cancels their renders.

  KEYS: Ctrl+1 for single font, Ctrl+2 for gallery, Ctrl+Tab to flip. Ctrl+=
        and Ctrl+- resize whichever view is showing. Double-clicking a gallery
        row still opens that font in the single-font view.

  DEVIATION FROM THE BLUEPRINT (Section 8), and why: the blueprint draws four
        flat tabs — Preview, All Fonts, Glyphs, Info. Glyphs and Info are both
        about the one selected font, so they belong inside the single-font view
        rather than beside the gallery. Phase 6 will add them there, as a tab
        strip within that view, which leaves the top-level switch meaning what
        it says: one font, or all of them. The single-font view hosts the
        preview directly for now, since a tab strip with one tab on it is just
        clutter.

  VERIFIED: 183 tests, all passing, zero build warnings. The switch, the toggle,
        double-click-to-open, per-view resizing and selection surviving a switch
        all have tests, as do the three converters and the preset naming. Small
        fits ten fonts on screen with the whole pangram visible where Medium
        fits seven and clips them.

Phase 4: the All Fonts gallery
  WHAT: The second tab: every font in the folder, each drawn in its own face.
        New Services/RenderedBitmapCache.cs, ViewModels/GalleryViewModel.cs,
        Controls/FontRenderImage.cs, Views/GalleryView, and
        Core/ObservableRangeCollection.cs.
  WHY:  Requirement R3. Reading a list of family names tells you very little
        about what a font looks like; seeing forty of them at once tells you
        immediately which three are worth a closer look.
  HOW:  The gallery binds to the same collection the sidebar does, so selection
        and the metadata pass are shared rather than duplicated. Rows do not
        render from the view model: each visible row's FontRenderImage asks for
        its own bitmap when it is handed a font and cancels that request the
        moment it is handed a different one, which is what keeps a fast scroll
        through two thousand fonts to a couple of dozen live requests instead of
        two thousand. Results are checked against the font the control is
        showing now before they are painted, because a recycled container can
        receive a result meant for the font it used to show. Finished bitmaps go
        into an LRU bounded by both a row count (300) and a byte budget (96 MB).

  TWO BUGS FOUND BY ACTUALLY RUNNING IT:
        - A folder of 1,322 fonts sat on "Scanning…" for over six seconds. The
          scanner was not at fault; filling an ObservableCollection one font at a
          time was, because every add is a change notification and every
          notification is a layout pass in each bound list. ObservableRangeCollection
          replaces the contents in one reset instead, and the same folder now
          lists in well under a second.
        - Windows FNT (.fon) fonts rendered as a row of identical boxes. They
          index their glyphs by raw byte value rather than by Unicode, so asking
          for code points returned glyph 0 for every character and the result was
          .notdef repeated. LoadedFace now chooses its character map
          deliberately — Unicode where there is one, the symbol map's private-use
          area where that is what the font has, raw byte values otherwise — and
          looks glyphs up accordingly. The Phase 1 test had passed throughout
          because .notdef is a filled box and the test only counted dark pixels;
          it now renders two different strings and demands different pixels.

  ALSO: switching to the gallery gives its list the keyboard focus, so Page Down
        and the arrow keys work without clicking first. Ctrl with the wheel
        resizes the rows, as in the Preview tab, and Ctrl+1 and Ctrl+2 switch
        tabs. Double-clicking a row takes you to the Preview tab. A font that
        will not open shows its error where its preview would be.

  VERIFIED: 169 tests, all passing, zero build warnings.
        - A folder of 1,322 files (1,361 rows after collections expand, 50 of
          them deliberately corrupt or zero-byte, 510 MB in all) lists in under
          a second and reports "1,361 fonts · 50 unreadable".
        - Scrolling 400 wheel notches deep through the gallery leaves the app
          responding, with a working set of 325-416 MB against the blueprint's
          400 MB target, and bitmap, CFF and web fonts all drawing correctly.
        - A thousand distinct rows rendered in sequence leave the cache at its
          own limits rather than at the number of fonts.
        - Forty rows started and abandoned mid-flight leave the gallery working.
        - The cache keys on everything that changes the pixels, evicts least
          recently used by both count and bytes, and refuses an unfrozen bitmap.

  NOTE ON MEMORY: the working set sits close to the 400 MB target with a
        510 MB folder open and the gallery scrolled through it. The face cache
        (64 faces or 256 MB) is the bulk of that and is already bounded; Phase 8

Phase 3: folder browsing and the Preview tab
  WHAT: The engine became an application. New Core/FontFile.cs (with a natural

  WHY:  Requirement R2: open one font and get the whole folder, so the user
        scrolls through fonts instead of opening files one at a time. Everything

  HOW:  Opening a file opens its folder and selects that file. The scanner
        touches directory entries only — no file is opened and nothing decoded —
        so the list appears at once; a background pass at Low priority then reads
        each file's metadata, replaces file names with family names, and expands
        collections into one row per face. The preview debounces every change by
        30 ms and cancels the request in flight, so holding a key costs one

          their Type 1 font instead, ready for favourites in Phase 5.
        - Collections cannot be expanded at scan time: how many faces a file

          the metadata.

          rather than failing (requirement R10).
        - Waterfall lines are clipped at the panel edge rather than wrapped, so
          the ladder of sizes stays comparable; the main preview wraps to the
          panel.
        - Ctrl+Down and Ctrl+Up are window-level bindings, so they work from

        - Navigation stops at the ends rather than wrapping: a held-down

        it has been opened, which happens in the background pass — by which time

  KEYS SO FAR: Ctrl+O, Ctrl+Shift+O, Ctrl+Down, Ctrl+Up, Ctrl+Home, Ctrl+End,

Phase 2: WOFF and WOFF 2.0
  WHAT: Managed decoders for both web font formats. New in Engine/Woff/:
        ByteReader, SfntWriter, WoffDecoder, Woff2Decoder and
        Woff2GlyfReconstructor; new Engine/FormatNormalizer.cs dispatches to
        them. .woff and .woff2 files now open, render, list their glyphs and
        report their metadata exactly like any other font.
  WHY:  Phase 1 left WOFF 1.0 working by accident (FreeType has zlib) and
        WOFF 2.0 not working at all (this prebuilt freetype.dll has no Brotli).
        Relying on whatever the native library happens to support is precisely
        what the blueprint warned against, so both formats are now decoded in
        managed code and FreeType only ever sees plain SFNT.
  HOW:  WOFF 1.0 is a 44-byte header plus a directory of raw or zlib-deflated
        tables. WOFF 2.0 is considerably more: tags replaced by indices into a
        fixed list of 63, lengths in a variable-width integer, every table's
        data concatenated into one Brotli stream, and the outline tables
        structurally rewritten. Woff2GlyfReconstructor puts glyf and loca back
        together from seven parallel streams, decoding point coordinates through
        the 128-entry triplet code, rebuilding composite glyphs, and recomputing
        the bounding boxes that were left out. A transformed hmtx has its left
        side bearings restored from those bounding boxes. SfntWriter reassembles
        everything, recomputing table checksums and head.checkSumAdjustment.

  BUG FOUND AND FIXED DURING THE PHASE: the bounding-box bitmap in a transformed
        glyf table is padded to a four-byte boundary, not to a whole byte. The
        first implementation rounded to a byte, which for Inter (2,933 glyphs)
        read 367 bytes where the format specifies 368. Everything following was
        then shifted by one byte, which left simple glyphs correct — their boxes
        are computed from their own points — and silently displaced every
        composite glyph instead, so accented capitals drifted while plain Latin
        looked perfect. Noto Sans and Noto Serif passed throughout, because
        their glyph counts happen to land where the two calculations agree.
        Only the pixel-for-pixel comparison against the original font caught it.
        WoffInternalsTests.CompositeGlyphsFromAWoff2_LandWhereTheOriginalPutsThem
        now guards it specifically.

  TEST FIXTURES: tools/make-test-fonts.py now also writes
        Inter-Regular-hmtxtransform.woff2 and Inter-Regular-notransform.woff2,
        so the hmtx transform and the all-null-transform path are both covered;
        the default writer only ever transforms glyf and loca. The .woff and
        .woff2 conversions are now made with recalcBBoxes and recalcTimestamp
        turned off, so a web font is byte-faithful to the font it came from and
        the decoders can be checked against it exactly rather than approximately.

  VERIFIED: 116 tests, all passing, zero build warnings.
        - All 10 X.ttf / X.woff / X.woff2 triples report the same glyph count
          and family name, and render pixel-for-pixel identically at 32 pt.
        - Decoding a .woff reproduces every table byte for byte, head aside,
          where only checkSumAdjustment may differ; decoding a .woff2 reproduces
          every table except glyf, loca and head, which are legitimately rebuilt.
        - The hmtx-transformed and no-transform WOFF2 variants both render
          identically to the original TTF.
        - CFF-outline, variable and composite-heavy fonts all survive the round
          trip; variable axes and glyph lists come through unchanged.
        - Truncated (at 2%, 10%, 50% and 95%), corrupted, zero-table,
          lying-length and decompression-bomb files all produce an error card,
          and 40 malformed files in a row leave the engine serving the next
          request.
        - A web font is not locked while it is open.
        - The published exe is still one file, 60.24 MB.

  DEVIATION FROM THE BLUEPRINT: a WOFF 2.0 file may hold a whole TrueType
        collection. This decoder parses the collection directory, validates its
        table indices, and then refuses the file with a message naming how many
        fonts are inside, rather than rebuilding it. Nothing available can
        produce such a file to test against — fontTools cannot write one — and
        an unverified reconstruction of a font format is worse than a clear
        refusal. The parse is still done so a collection can never be mistaken
        for a single font and silently mis-decoded.

  ALSO: InternalsVisibleTo was added for the test project. The decoders are
        internal, but they are exactly the kind of code that deserves direct
        unit tests of its own — variable-length integers, checksum arithmetic,
        table layout — rather than only being exercised through a rendered page.

Phase 1: font engine core
  WHAT: The real engine, replacing the Phase 0 spike. New in Core/: FontFormat,
        FormatSniffer, FaceKey, FaceSummary, FontInfo and the render types. New
        in Engine/: FontEngine (the dedicated thread), EngineJob, FaceCache,
        LoadedFace, TextLayout, GlyphRasterizer, MetadataReader and
        FreeTypeNative. New in Services/: RenderService, the public async API.
        Engine/FreeTypeSpike.cs and its tests are gone.
  WHY:  Everything above this layer — folder browsing, the gallery, favourites,
        the glyph map, the Info tab — is a client of these five calls. Getting
        the threading, the cancellation and the no-lock rule right once here is
        what keeps the rest of the phases ordinary UI work.
  HOW:  One background thread named FontEngine owns the FT_Library and every
        face. Work reaches it through two queues, High and Low, drained strictly
        High-first, so a thousand queued gallery rows cannot delay the selected
        font's preview. Every job carries a CancellationToken, checked when it
        reaches the front of the queue and again inside the job. Faces are read
        whole into pinned memory over a FileShare.ReadWrite|Delete handle and
        opened with FT_New_Memory_Face, so no font file is ever locked. A
        least-recently-used FaceCache holds 64 faces or 256 MB, whichever comes
        first. RenderService hands the UI nothing but plain data.

  DETAIL WORTH KNOWING:
        - FormatSniffer reads magic bytes first and the extension only as a
          fallback, so a CFF font named .ttf opens as what it is. MZ counts as a
          font only when the name agrees, because every Windows executable
          starts that way.
        - TextLayout has two paths: HarfBuzz for SFNT fonts, and FreeType's own
          cmap plus kern table for Type 1, BDF, PCF and Windows FNT, which
          HarfBuzz cannot take. Both feed one shared line-breaker, which wraps on
          spaces and falls back to breaking inside a word too long for the panel
          rather than dropping it.
        - GlyphRasterizer handles every pixel mode FreeType emits: 8-bit
          coverage, 1-bit from bitmap fonts, the 2- and 4-bit forms (normalised
          through FT_Bitmap_Convert rather than unpacked by hand), and
          premultiplied BGRA from colour fonts.
        - Bitmap fonts snap to their nearest available strike via FT_Select_Size
          instead of failing at a size they do not have.
        - Type 1 fonts get their .afm/.pfm metrics attached from memory with
          FT_Attach_Stream, which keeps the no-lock rule and sidesteps FreeType's
          byte-oriented path handling for non-ASCII names.
        - MetadataReader scores name records rather than taking the first:
          Windows/English wins, then Unicode, then Mac Roman. Type 1, WinFNT and
          BDF/PCF metadata come from their own accessors.

  ADDED BINDINGS: FreeTypeSharp 3.1.0 does not bind the metadata accessors, so
        Engine/FreeTypeNative.cs declares FT_Get_Sfnt_Name(_Count),
        FT_Get_PS_Font_Info, FT_Get_WinFNT_Header, FT_Get_BDF_Property,
        FT_Get_Font_Format, FT_Get_MM_Var and FT_Done_MM_Var against the same
        freetype.dll the package already ships, where all of them are exported.
        Before relying on this, the FT_FaceRec_ layout was checked against a
        known font: this build uses a 64-bit FT_Long, matching the binding's
        structs, so units_per_EM, num_glyphs and the name pointers all read
        correctly. Where FreeType writes into a caller-supplied record
        (FT_WinFNT_HeaderRec, BDF_PropertyRec), an oversized zeroed buffer is
        passed and fields are read at fixed offsets, so a future FreeType that
        grew one of those records could not overwrite the stack.

  VERIFIED: 76 tests, all passing, zero build warnings.
        - Every one of the 17 non-web corpus fonts opens, reports a family name,
          and renders visible ink: variable and static TTF, CFF-outline OTF, TTC,
          Type 1, BDF, PCF and Windows FON.
        - TestCollection.ttc reports both faces separately, and the two render
          differently. cambria.ttc enumerates its faces.
        - Inter's variable axes come back as wght and opsz with sane
          minimum/default/maximum ordering, plus named instances.
        - Bitmap fonts report their fixed sizes, are marked not scalable, and
          render after snapping from a size they do not have (41 px).
        - Segoe UI Emoji renders in actual colour through the BGRA path.
        - Microsoft YaHei lists over 10,000 glyphs in ascending code-point order.
        - A font deleted while it is on screen stays deleted, and the cached face
          keeps rendering from memory; a font can be overwritten in place.
        - Garbage, zero-byte, truncated and missing files produce an error row
          rather than an exception, and the engine thread survives to serve the
          next request.
        - 60 overlapping requests across both priorities all settle; a cancelled
          request throws rather than completing; a one-face cache evicts.
        - The published exe is still one file, 60.23 MB, and from an empty folder
          renders a wrapped pangram with full metadata in 70 ms.

  KNOWN STATE: WOFF 1.0 files open, because FreeType always has zlib. WOFF 2.0
        files do not, because this prebuilt freetype.dll has no Brotli — exactly
        the reason the blueprint asks for managed decoders instead of trusting
        the native library. A test pins both halves of that down, and Phase 2
        turns it into "both open".

  DEVIATIONS FROM THE BLUEPRINT, and why:
        - RenderGlyphCellsAsync takes GlyphEntry values rather than bare code
          points. The Glyphs tab has to be able to show glyphs no code point
          reaches (section 8.5, "Show unmapped glyphs"), and a code point cannot
          name one.
        - Core/FontFile.cs is not here. Nothing in the engine uses it; it arrives
