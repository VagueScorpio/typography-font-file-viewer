 v1.0.0 (unreleased)

Test fonts: fonttools corpus builder
  WHAT: Added tools/ with requirements.txt (fonttools[woff] 4.68.0, pinned),
        make-test-fonts.py and a README. The script builds the whole test-font
        corpus into the git-ignored tests/fonts/ folder.
  WHY:  Phase 2 checks the WOFF and WOFF 2.0 decoders by opening X.ttf, X.woff
        and X.woff2 and demanding the same glyph count, family name and
        outlines. Those triples have to be generated from one original, which
        is exactly what fonttools is for. Standing the tooling up before
        Phase 1 means the engine work can be tested against real fonts in every
        supported format from its first commit, rather than against Arial alone.
  HOW:  fonttools is installed into tools/.venv (git-ignored) so nothing touches
        the system Python. The script fetches open-licensed sources, derives
        wght 400/700 static instances from each variable font with
        fontTools.varLib.instancer, packs two of them into a TestCollection.ttc,
        then writes .woff and .woff2 beside every SFNT font by setting
        TTFont.flavor. It re-runs idempotently (--force rebuilds, --no-fetch
        works offline) and verifies every triple before reporting.

  CORPUS BUILT (19.6 MB, 37 files, none committed):
        9 .ttf   - Inter, Noto Sans, Noto Serif as variable fonts plus derived
                   Regular/Bold statics
        1 .otf   - Source Serif 4, CFF outlines rather than TrueType
        1 .ttc   - two faces, built here
        10 .woff + 10 .woff2 - one pair per SFNT font, all verified as matching
                   triples
        1 .pfa   - URW Nimbus Roman, PostScript Type 1
        1 .bdf, 2 .pcf, 2 .fon - Spleen, the same bitmap font in all three
                   containers

  NOT COVERED: .dfont, which needs a macOS data-fork suitcase. There is no open
        source to fetch and nothing on Windows produces one, so it is noted in
        tests/fonts/README.md as a manual step. Windows system fonts
        (cambria.ttc, msyh.ttc, seguiemj.ttf, the .fon files) are read in place
        and deliberately never copied into the repository.

  NOTE: The URW Type 1 font arrives as PFA (ASCII) rather than PFB (binary), so
        the script sniffs the magic bytes and names the file accordingly instead
        of trusting the source's .t1 extension — the same magic-bytes-first rule
        the app itself uses.

Phase 0: scaffold and de-risk
  WHAT: The solution now builds, tests and publishes. Added
        TypographyFontFileViewer.slnx, the app project (WPF, net10.0-windows,
        self-contained single-file win-x64), app.manifest, a generated
        Assets/app.ico, App.xaml(.cs), MainWindow.xaml(.cs),
        Core/FontLoadException.cs, Engine/FreeTypeSpike.cs, and an xUnit v3 test
        project with 8 passing tests.
  WHY:  Phase 0 exists to prove the risky part before any feature work: that
        FreeType and HarfBuzz really do run from inside a single self-contained
        exe, on a machine with nothing installed, and that fonts can be read
        without locking them.
  HOW:  FreeTypeSpike reads the font fully into memory over a
        FileShare.ReadWrite|Delete handle, pins the bytes, hands the same
        pointer to FT_New_Memory_Face and to a HarfBuzz Blob, shapes the string
        with HarfBuzz, rasterizes each glyph with FreeType and composites 8-bit
        coverage (GRAY and MONO pixel modes) into a BGRA buffer. The engine
        returns plain bytes; MainWindow builds and freezes the BitmapSource, so
        no native handle and no WPF object ever cross the boundary.

  VERIFIED:
        - 8/8 tests pass: face summary, ink present, size scaling, blank text,
          no file lock (the file is deleted while "open"), and garbage, empty
          and missing files all raising FontLoadException rather than crashing.
        - publish.bat produces ONE file: publish\TypographyFontFileViewer.exe,
          60.2 MB (63,109,298 bytes).
        - That exe, alone in an empty folder, renders "Hello" in Arial Regular
          (4,652 glyphs), 5 characters shaped into 5 glyphs by HarfBuzz.
        - Per-Monitor V2 works: 72 pt at 120 DPI resolved to 120 px.
        - Time to window: 826 ms first run (includes self-extraction), then
          741 ms and 604 ms. Target is under 2 s.
        - The app wrote nothing beside the exe.

  PACKAGES (all MIT, pinned):
        FreeTypeSharp 3.1.0 (the main package, not the McEndu fork; it ships
        runtimes/win-x64/native/freetype.dll), HarfBuzzSharp 14.4.0 with
        HarfBuzzSharp.NativeAssets.Win32 14.4.0, CommunityToolkit.Mvvm 8.4.2.
        Tests: xunit.v3 4.0.2, xunit.runner.visualstudio 4.0.1.

  DEVIATIONS FROM THE BLUEPRINT (Section 11), and why:
        - The solution is TypographyFontFileViewer.slnx, not .sln. The .NET 10
          SDK emits the XML solution format by default; Visual Studio 2022
          17.14+ and Rider both read it.
        - Added global.json with the test runner set to
          Microsoft.Testing.Platform. xUnit v3 runs on that platform, and the
          .NET 10 SDK refuses to run it through dotnet test without this opt-in.
        - Added a RemovePdbsFromPublish target to the csproj. The HarfBuzz
          native assets package drops a 22.8 MB libHarfBuzzSharp.pdb into the
          publish folder, and the deliverable must be the exe alone.
        - The test project sets SelfContained=true to match the app project; a
          self-contained exe cannot be referenced by a framework-dependent one
          (NETSDK1151).

  NOT YET DONE: Engine/FreeTypeSpike.cs is scaffolding for this phase only.
        Phase 1 replaces it with FontEngine, FaceCache, TextLayout,
        GlyphRasterizer and MetadataReader, and adds the remaining pixel modes
        (GRAY2/GRAY4/LCD/BGRA), TTC face enumeration and Type 1 companions.

Naming: Typography Font File Viewer
  WHAT: Renamed the app, the assembly, the exe, the settings file, the project
        folders and the GitHub repository from "Simple Font Viewer" to
        "Typography Font File Viewer" (repo: typography-font-file-viewer).
  WHY:  The project's chosen name.
  HOW:  Renamed the blueprint and project folders, replaced the name and the
        SimpleFontViewer identifier across every document, and renamed the
        GitHub repository. The blueprint's reference to the unrelated "Simple
        Rich Text Editor" was deliberately left alone.

Repository scaffold
  WHAT: Created the public git repository: blueprint document, README, this
        changelog, .gitignore, publish.bat, MIT license, and the folder tree
        from Section 11.1 of the blueprint.
  WHY:  The build runs phase by phase (blueprint Section 12). The repository,
        its conventions and its ignore rules have to exist before Phase 0 so
        every phase can commit into a clean history.
  HOW:  git init; files written from the blueprint's Sections 10, 11 and 16.
        .gitignore excludes build output, every .pdb, the downloaded test fonts
        in tests/fonts/, and the files the portable app writes next to the exe.
