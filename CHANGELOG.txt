View switch: single font or gallery   (requested, outside the phase plan)
  WHAT: The tab strip is gone. A segmented switch in the header moves between
        two views — Single font and Gallery — and the gallery gained four named
        sizes: S (16 pt), M (28 pt), L (44 pt) and XL (72 pt), alongside the
        slider it already had. New ViewModels/ViewMode.cs and three converters;
        MainWindow now shows one of two views rather than hosting tabs.
  WHY:  Asked for directly. Both views already existed as tabs, but tabs say
        "panels of the same thing", and these are two answers to different
        questions: "what does this font look like?" against "which of these
        fonts do I want?". A switch says that, and the named sizes save aiming
        at a slider for the sizes anyone actually wants.
  HOW:  Radio buttons sharing a group, styled as one control, bound to a
        ViewMode enum through EnumToBooleanConverter; the views themselves swap
        on EnumToVisibilityConverter. The size presets are positions on the same
        scale the slider moves along rather than a separate setting, so picking
        Large and dragging the slider to 44 do the same thing and a preset
        lights up whenever the slider lands on it. Both views stay loaded, so
        switching keeps each one's scroll position; the hidden one unloads its
        rows, which cancels their renders.

  KEYS: Ctrl+1 for single font, Ctrl+2 for gallery, Ctrl+Tab to flip. Ctrl+=
        and Ctrl+- resize whichever view is showing. Double-clicking a gallery
        row still opens that font in the single-font view.

  DEVIATION FROM THE BLUEPRINT (Section 8), and why: the blueprint draws four
        flat tabs — Preview, All Fonts, Glyphs, Info. Glyphs and Info are both
        about the one selected font, so they belong inside the single-font view
        rather than beside the gallery. Phase 6 will add them there, as a tab
        strip within that view, which leaves the top-level switch meaning what
        it says: one font, or all of them. The single-font view hosts the
        preview directly for now, since a tab strip with one tab on it is just
        clutter.

  VERIFIED: 183 tests, all passing, zero build warnings. The switch, the toggle,
        double-click-to-open, per-view resizing and selection surviving a switch
        all have tests, as do the three converters and the preset naming. Small
        fits ten fonts on screen with the whole pangram visible where Medium
        fits seven and clips them.

Phase 4: the All Fonts gallery
  WHAT: The second tab: every font in the folder, each drawn in its own face.
        New Services/RenderedBitmapCache.cs, ViewModels/GalleryViewModel.cs,
        Controls/FontRenderImage.cs, Views/GalleryView, and
        Core/ObservableRangeCollection.cs.
  WHY:  Requirement R3. Reading a list of family names tells you very little
        about what a font looks like; seeing forty of them at once tells you
        immediately which three are worth a closer look.
  HOW:  The gallery binds to the same collection the sidebar does, so selection
        and the metadata pass are shared rather than duplicated. Rows do not
        render from the view model: each visible row's FontRenderImage asks for
        its own bitmap when it is handed a font and cancels that request the
        moment it is handed a different one, which is what keeps a fast scroll
        through two thousand fonts to a couple of dozen live requests instead of
        two thousand. Results are checked against the font the control is
        showing now before they are painted, because a recycled container can
        receive a result meant for the font it used to show. Finished bitmaps go
        into an LRU bounded by both a row count (300) and a byte budget (96 MB).

  TWO BUGS FOUND BY ACTUALLY RUNNING IT:
        - A folder of 1,322 fonts sat on "Scanning…" for over six seconds. The
          scanner was not at fault; filling an ObservableCollection one font at a
          time was, because every add is a change notification and every
          notification is a layout pass in each bound list. ObservableRangeCollection
          replaces the contents in one reset instead, and the same folder now
          lists in well under a second.
        - Windows FNT (.fon) fonts rendered as a row of identical boxes. They
          index their glyphs by raw byte value rather than by Unicode, so asking
          for code points returned glyph 0 for every character and the result was
          .notdef repeated. LoadedFace now chooses its character map
          deliberately — Unicode where there is one, the symbol map's private-use
          area where that is what the font has, raw byte values otherwise — and
          looks glyphs up accordingly. The Phase 1 test had passed throughout
          because .notdef is a filled box and the test only counted dark pixels;
          it now renders two different strings and demands different pixels.

  ALSO: switching to the gallery gives its list the keyboard focus, so Page Down
        and the arrow keys work without clicking first. Ctrl with the wheel
        resizes the rows, as in the Preview tab, and Ctrl+1 and Ctrl+2 switch
        tabs. Double-clicking a row takes you to the Preview tab. A font that
        will not open shows its error where its preview would be.

  VERIFIED: 169 tests, all passing, zero build warnings.
        - A folder of 1,322 files (1,361 rows after collections expand, 50 of
          them deliberately corrupt or zero-byte, 510 MB in all) lists in under
          a second and reports "1,361 fonts · 50 unreadable".
        - Scrolling 400 wheel notches deep through the gallery leaves the app
          responding, with a working set of 325-416 MB against the blueprint's
          400 MB target, and bitmap, CFF and web fonts all drawing correctly.
        - A thousand distinct rows rendered in sequence leave the cache at its
          own limits rather than at the number of fonts.
        - Forty rows started and abandoned mid-flight leave the gallery working.
        - The cache keys on everything that changes the pixels, evicts least
          recently used by both count and bytes, and refuses an unfrozen bitmap.

  NOTE ON MEMORY: the working set sits close to the 400 MB target with a
        510 MB folder open and the gallery scrolled through it. The face cache
        (64 faces or 256 MB) is the bulk of that and is already bounded; Phase 8
        is where the stress list gets run properly and these numbers get tuned.

Phase 3: folder browsing and the Preview tab
  WHAT: The engine became an application. New Core/FontFile.cs (with a natural
        file-name comparer), Services/FolderScanner.cs, the MVVM layer
        (MainViewModel, FontItemViewModel, PreviewViewModel),
        Views/FontListView and Views/PreviewView, Controls/Converters.cs, and a
        rebuilt MainWindow with a menu, a toolbar, a resizable sidebar and a
        status bar.
  WHY:  Requirement R2: open one font and get the whole folder, so the user
        scrolls through fonts instead of opening files one at a time. Everything
        from Phase 1 and 2 was reachable only from tests until now.
  HOW:  Opening a file opens its folder and selects that file. The scanner
        touches directory entries only — no file is opened and nothing decoded —
        so the list appears at once; a background pass at Low priority then reads
        each file's metadata, replaces file names with family names, and expands
        collections into one row per face. The preview debounces every change by
        30 ms and cancels the request in flight, so holding a key costs one
        render rather than thirty.

  DETAIL WORTH KNOWING:
        - Natural ordering: "Font2" sorts before "Font10". Plain string order
          puts "Font10" first, and numbered weights are common enough that the
          wrong order is noticeable immediately.
        - Companions (.afm, .pfm, .inf) are hidden from the list and attached to
          their Type 1 font instead, ready for favourites in Phase 5.
        - Collections cannot be expanded at scan time: how many faces a file
          holds is not knowable until it has been opened. The rows appear with
          the metadata.
        - A font that will not open still gets a row, marked with a warning and
          carrying its error in the tooltip, and selecting it clears the preview
          rather than failing (requirement R10).
        - Waterfall lines are clipped at the panel edge rather than wrapped, so
          the ladder of sizes stays comparable; the main preview wraps to the
          panel.
        - Ctrl+Down and Ctrl+Up are window-level bindings, so they work from
          inside the preview text box, and the list scrolls to follow.
        - Navigation stops at the ends rather than wrapping: a held-down
          Ctrl+Down that cycled for ever would never show it had finished.

  BUG FOUND AND FIXED DURING THE PHASE: a font is not known to be broken until
        it has been opened, which happens in the background pass — by which time
        the preview may already be pointed at it. Selecting the row again
        changed nothing, because the selection had not changed. The preview is
        now re-synchronised when metadata arrives for the row already on screen.

  KEYS SO FAR: Ctrl+O, Ctrl+Shift+O, Ctrl+Down, Ctrl+Up, Ctrl+Home, Ctrl+End,
        F5, Ctrl+= and Ctrl+- for size, and Ctrl with the mouse wheel over the
        preview. The rest of Section 9 arrives with the features they belong to.

  VERIFIED: 149 tests, all passing, zero build warnings.
        - Opening Inter-Bold.ttf lists all 40 fonts in the folder with that one
          selected, and the status bar reads "Font 6 of 40".
        - The scanner finds every format in the corpus, hides companions while
          attaching them, sorts naturally, honours the subfolder switch, and
          returns nothing rather than throwing for a folder that is not there.
        - The metadata pass replaces file names with family names; a collection
          becomes two rows labelled (1/2) and (2/2); a corrupt file becomes one
          marked row and leaves its neighbour alone.
        - Next and previous walk all five fonts of a folder and back, and stop
          at both ends.
        - Rescan picks up a font added after the folder was opened and keeps the
          selection.
        - A bitmap font reports the sizes it actually has.
        - The published exe is still one file, 60.28 MB, and writes nothing
          beside itself.

  NOT YET DONE: the search box, the subfolder toggle, sort options and recent
        folders are Phase 7; the star column and the Favourites button are Phase
        5; the All Fonts, Glyphs and Info tabs are Phases 4 and 6. The tab strip
        currently holds Preview alone.

Phase 2: WOFF and WOFF 2.0
  WHAT: Managed decoders for both web font formats. New in Engine/Woff/:
        ByteReader, SfntWriter, WoffDecoder, Woff2Decoder and
        Woff2GlyfReconstructor; new Engine/FormatNormalizer.cs dispatches to
        them. .woff and .woff2 files now open, render, list their glyphs and
        report their metadata exactly like any other font.
  WHY:  Phase 1 left WOFF 1.0 working by accident (FreeType has zlib) and
        WOFF 2.0 not working at all (this prebuilt freetype.dll has no Brotli).
        Relying on whatever the native library happens to support is precisely
        what the blueprint warned against, so both formats are now decoded in
        managed code and FreeType only ever sees plain SFNT.
  HOW:  WOFF 1.0 is a 44-byte header plus a directory of raw or zlib-deflated
        tables. WOFF 2.0 is considerably more: tags replaced by indices into a
        fixed list of 63, lengths in a variable-width integer, every table's
        data concatenated into one Brotli stream, and the outline tables
        structurally rewritten. Woff2GlyfReconstructor puts glyf and loca back
        together from seven parallel streams, decoding point coordinates through
        the 128-entry triplet code, rebuilding composite glyphs, and recomputing
        the bounding boxes that were left out. A transformed hmtx has its left
        side bearings restored from those bounding boxes. SfntWriter reassembles
        everything, recomputing table checksums and head.checkSumAdjustment.

  BUG FOUND AND FIXED DURING THE PHASE: the bounding-box bitmap in a transformed
        glyf table is padded to a four-byte boundary, not to a whole byte. The
        first implementation rounded to a byte, which for Inter (2,933 glyphs)
        read 367 bytes where the format specifies 368. Everything following was
        then shifted by one byte, which left simple glyphs correct — their boxes
        are computed from their own points — and silently displaced every
        composite glyph instead, so accented capitals drifted while plain Latin
        looked perfect. Noto Sans and Noto Serif passed throughout, because
        their glyph counts happen to land where the two calculations agree.
        Only the pixel-for-pixel comparison against the original font caught it.
        WoffInternalsTests.CompositeGlyphsFromAWoff2_LandWhereTheOriginalPutsThem
        now guards it specifically.

  TEST FIXTURES: tools/make-test-fonts.py now also writes
        Inter-Regular-hmtxtransform.woff2 and Inter-Regular-notransform.woff2,
        so the hmtx transform and the all-null-transform path are both covered;
        the default writer only ever transforms glyf and loca. The .woff and
        .woff2 conversions are now made with recalcBBoxes and recalcTimestamp
        turned off, so a web font is byte-faithful to the font it came from and
        the decoders can be checked against it exactly rather than approximately.

  VERIFIED: 116 tests, all passing, zero build warnings.
        - All 10 X.ttf / X.woff / X.woff2 triples report the same glyph count
          and family name, and render pixel-for-pixel identically at 32 pt.
        - Decoding a .woff reproduces every table byte for byte, head aside,
          where only checkSumAdjustment may differ; decoding a .woff2 reproduces
          every table except glyf, loca and head, which are legitimately rebuilt.
        - The hmtx-transformed and no-transform WOFF2 variants both render
          identically to the original TTF.
        - CFF-outline, variable and composite-heavy fonts all survive the round
          trip; variable axes and glyph lists come through unchanged.
        - Truncated (at 2%, 10%, 50% and 95%), corrupted, zero-table,
          lying-length and decompression-bomb files all produce an error card,
          and 40 malformed files in a row leave the engine serving the next
          request.
        - A web font is not locked while it is open.
        - The published exe is still one file, 60.24 MB.

  DEVIATION FROM THE BLUEPRINT: a WOFF 2.0 file may hold a whole TrueType
        collection. This decoder parses the collection directory, validates its
        table indices, and then refuses the file with a message naming how many
        fonts are inside, rather than rebuilding it. Nothing available can
        produce such a file to test against — fontTools cannot write one — and
        an unverified reconstruction of a font format is worse than a clear
        refusal. The parse is still done so a collection can never be mistaken
        for a single font and silently mis-decoded.

  ALSO: InternalsVisibleTo was added for the test project. The decoders are
        internal, but they are exactly the kind of code that deserves direct
        unit tests of its own — variable-length integers, checksum arithmetic,
        table layout — rather than only being exercised through a rendered page.

Phase 1: font engine core
  WHAT: The real engine, replacing the Phase 0 spike. New in Core/: FontFormat,
        FormatSniffer, FaceKey, FaceSummary, FontInfo and the render types. New
        in Engine/: FontEngine (the dedicated thread), EngineJob, FaceCache,
        LoadedFace, TextLayout, GlyphRasterizer, MetadataReader and
        FreeTypeNative. New in Services/: RenderService, the public async API.
        Engine/FreeTypeSpike.cs and its tests are gone.
  WHY:  Everything above this layer — folder browsing, the gallery, favourites,
        the glyph map, the Info tab — is a client of these five calls. Getting
        the threading, the cancellation and the no-lock rule right once here is
        what keeps the rest of the phases ordinary UI work.
  HOW:  One background thread named FontEngine owns the FT_Library and every
        face. Work reaches it through two queues, High and Low, drained strictly
        High-first, so a thousand queued gallery rows cannot delay the selected
        font's preview. Every job carries a CancellationToken, checked when it
        reaches the front of the queue and again inside the job. Faces are read
        whole into pinned memory over a FileShare.ReadWrite|Delete handle and
        opened with FT_New_Memory_Face, so no font file is ever locked. A
        least-recently-used FaceCache holds 64 faces or 256 MB, whichever comes
        first. RenderService hands the UI nothing but plain data.

  DETAIL WORTH KNOWING:
        - FormatSniffer reads magic bytes first and the extension only as a
          fallback, so a CFF font named .ttf opens as what it is. MZ counts as a
          font only when the name agrees, because every Windows executable
          starts that way.
        - TextLayout has two paths: HarfBuzz for SFNT fonts, and FreeType's own
          cmap plus kern table for Type 1, BDF, PCF and Windows FNT, which
          HarfBuzz cannot take. Both feed one shared line-breaker, which wraps on
          spaces and falls back to breaking inside a word too long for the panel
          rather than dropping it.
        - GlyphRasterizer handles every pixel mode FreeType emits: 8-bit
          coverage, 1-bit from bitmap fonts, the 2- and 4-bit forms (normalised
          through FT_Bitmap_Convert rather than unpacked by hand), and
          premultiplied BGRA from colour fonts.
        - Bitmap fonts snap to their nearest available strike via FT_Select_Size
          instead of failing at a size they do not have.
        - Type 1 fonts get their .afm/.pfm metrics attached from memory with
          FT_Attach_Stream, which keeps the no-lock rule and sidesteps FreeType's
          byte-oriented path handling for non-ASCII names.
        - MetadataReader scores name records rather than taking the first:
          Windows/English wins, then Unicode, then Mac Roman. Type 1, WinFNT and
          BDF/PCF metadata come from their own accessors.

  ADDED BINDINGS: FreeTypeSharp 3.1.0 does not bind the metadata accessors, so
        Engine/FreeTypeNative.cs declares FT_Get_Sfnt_Name(_Count),
        FT_Get_PS_Font_Info, FT_Get_WinFNT_Header, FT_Get_BDF_Property,
        FT_Get_Font_Format, FT_Get_MM_Var and FT_Done_MM_Var against the same
        freetype.dll the package already ships, where all of them are exported.
        Before relying on this, the FT_FaceRec_ layout was checked against a
        known font: this build uses a 64-bit FT_Long, matching the binding's
        structs, so units_per_EM, num_glyphs and the name pointers all read
        correctly. Where FreeType writes into a caller-supplied record
        (FT_WinFNT_HeaderRec, BDF_PropertyRec), an oversized zeroed buffer is
        passed and fields are read at fixed offsets, so a future FreeType that
        grew one of those records could not overwrite the stack.

  VERIFIED: 76 tests, all passing, zero build warnings.
        - Every one of the 17 non-web corpus fonts opens, reports a family name,
          and renders visible ink: variable and static TTF, CFF-outline OTF, TTC,
          Type 1, BDF, PCF and Windows FON.
        - TestCollection.ttc reports both faces separately, and the two render
          differently. cambria.ttc enumerates its faces.
        - Inter's variable axes come back as wght and opsz with sane
          minimum/default/maximum ordering, plus named instances.
        - Bitmap fonts report their fixed sizes, are marked not scalable, and
          render after snapping from a size they do not have (41 px).
        - Segoe UI Emoji renders in actual colour through the BGRA path.
        - Microsoft YaHei lists over 10,000 glyphs in ascending code-point order.
        - A font deleted while it is on screen stays deleted, and the cached face
          keeps rendering from memory; a font can be overwritten in place.
        - Garbage, zero-byte, truncated and missing files produce an error row
          rather than an exception, and the engine thread survives to serve the
          next request.
        - 60 overlapping requests across both priorities all settle; a cancelled
          request throws rather than completing; a one-face cache evicts.
        - The published exe is still one file, 60.23 MB, and from an empty folder
          renders a wrapped pangram with full metadata in 70 ms.

  KNOWN STATE: WOFF 1.0 files open, because FreeType always has zlib. WOFF 2.0
        files do not, because this prebuilt freetype.dll has no Brotli — exactly
        the reason the blueprint asks for managed decoders instead of trusting
        the native library. A test pins both halves of that down, and Phase 2
        turns it into "both open".

  DEVIATIONS FROM THE BLUEPRINT, and why:
        - RenderGlyphCellsAsync takes GlyphEntry values rather than bare code
          points. The Glyphs tab has to be able to show glyphs no code point
          reaches (section 8.5, "Show unmapped glyphs"), and a code point cannot
          name one.
        - Core/FontFile.cs is not here. Nothing in the engine uses it; it arrives
          with FolderScanner in Phase 3 rather than sitting unused.

Test fonts: fonttools corpus builder
  WHAT: Added tools/ with requirements.txt (fonttools[woff] 4.68.0, pinned),
        make-test-fonts.py and a README. The script builds the whole test-font
        corpus into the git-ignored tests/fonts/ folder.
  WHY:  Phase 2 checks the WOFF and WOFF 2.0 decoders by opening X.ttf, X.woff
        and X.woff2 and demanding the same glyph count, family name and
        outlines. Those triples have to be generated from one original, which
        is exactly what fonttools is for. Standing the tooling up before
        Phase 1 means the engine work can be tested against real fonts in every
        supported format from its first commit, rather than against Arial alone.
  HOW:  fonttools is installed into tools/.venv (git-ignored) so nothing touches
        the system Python. The script fetches open-licensed sources, derives
        wght 400/700 static instances from each variable font with
        fontTools.varLib.instancer, packs two of them into a TestCollection.ttc,
        then writes .woff and .woff2 beside every SFNT font by setting
        TTFont.flavor. It re-runs idempotently (--force rebuilds, --no-fetch
        works offline) and verifies every triple before reporting.

  CORPUS BUILT (19.6 MB, 37 files, none committed):
        9 .ttf   - Inter, Noto Sans, Noto Serif as variable fonts plus derived
                   Regular/Bold statics
        1 .otf   - Source Serif 4, CFF outlines rather than TrueType
        1 .ttc   - two faces, built here
        10 .woff + 10 .woff2 - one pair per SFNT font, all verified as matching
                   triples
        1 .pfa   - URW Nimbus Roman, PostScript Type 1
        1 .bdf, 2 .pcf, 2 .fon - Spleen, the same bitmap font in all three
                   containers

  NOT COVERED: .dfont, which needs a macOS data-fork suitcase. There is no open
        source to fetch and nothing on Windows produces one, so it is noted in
        tests/fonts/README.md as a manual step. Windows system fonts
        (cambria.ttc, msyh.ttc, seguiemj.ttf, the .fon files) are read in place
        and deliberately never copied into the repository.

  NOTE: The URW Type 1 font arrives as PFA (ASCII) rather than PFB (binary), so
        the script sniffs the magic bytes and names the file accordingly instead
        of trusting the source's .t1 extension — the same magic-bytes-first rule
        the app itself uses.

Phase 0: scaffold and de-risk
  WHAT: The solution now builds, tests and publishes. Added
        TypographyFontFileViewer.slnx, the app project (WPF, net10.0-windows,
        self-contained single-file win-x64), app.manifest, a generated
        Assets/app.ico, App.xaml(.cs), MainWindow.xaml(.cs),
        Core/FontLoadException.cs, Engine/FreeTypeSpike.cs, and an xUnit v3 test
        project with 8 passing tests.
  WHY:  Phase 0 exists to prove the risky part before any feature work: that
        FreeType and HarfBuzz really do run from inside a single self-contained
        exe, on a machine with nothing installed, and that fonts can be read
        without locking them.
  HOW:  FreeTypeSpike reads the font fully into memory over a
        FileShare.ReadWrite|Delete handle, pins the bytes, hands the same
        pointer to FT_New_Memory_Face and to a HarfBuzz Blob, shapes the string
        with HarfBuzz, rasterizes each glyph with FreeType and composites 8-bit
        coverage (GRAY and MONO pixel modes) into a BGRA buffer. The engine
        returns plain bytes; MainWindow builds and freezes the BitmapSource, so
        no native handle and no WPF object ever cross the boundary.

  VERIFIED:
        - 8/8 tests pass: face summary, ink present, size scaling, blank text,
          no file lock (the file is deleted while "open"), and garbage, empty
          and missing files all raising FontLoadException rather than crashing.
        - publish.bat produces ONE file: publish\TypographyFontFileViewer.exe,
          60.2 MB (63,109,298 bytes).
        - That exe, alone in an empty folder, renders "Hello" in Arial Regular
          (4,652 glyphs), 5 characters shaped into 5 glyphs by HarfBuzz.
        - Per-Monitor V2 works: 72 pt at 120 DPI resolved to 120 px.
        - Time to window: 826 ms first run (includes self-extraction), then
          741 ms and 604 ms. Target is under 2 s.
        - The app wrote nothing beside the exe.

  PACKAGES (all MIT, pinned):
        FreeTypeSharp 3.1.0 (the main package, not the McEndu fork; it ships
        runtimes/win-x64/native/freetype.dll), HarfBuzzSharp 14.4.0 with
        HarfBuzzSharp.NativeAssets.Win32 14.4.0, CommunityToolkit.Mvvm 8.4.2.
        Tests: xunit.v3 4.0.2, xunit.runner.visualstudio 4.0.1.
